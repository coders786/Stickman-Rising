# 1. RENDERING PARADIGM — 2.8D DEPTH-AWARE PERSPECTENCE

## 1.1 Dimensional Definition

This is NOT a flat 2D game. This is NOT a 3D game. This is **2.8D** — defined as follows:

- **Gameplay plane:** All gameplay-critical movement, hitbox detection, collision, and combat mechanics operate on a 2D plane (Z = 0). Input is mapped to X (horizontal) and Y (vertical) axes on this plane.
- **Rendering pipeline:** The entire visual output is rendered using a 3D rendering pipeline with perspective projection. Characters, enemies, and key gameplay objects are 3D meshes rendered with perspective correction.
- **Depth layering:** The environment extends into Z-space across 6 distinct parallax layers (specified in Section 10). Each layer moves at a defined rate relative to camera motion.
- **Z-axis excursions:** Characters MAY move along the Z-axis during specific scripted sequences (cinematic dashes, finishers, dodge rolls). These excursions are limited to ±5 units from the combat plane, are camera-controlled, last no more than 1.5 seconds, and do NOT affect gameplay hitboxes (the character's combat hitbox remains locked to Z = 0 during the entire excursion).
- **Perspective correctness:** Objects closer to the camera render larger. The perspective FOV is 35° (vertical). Camera distance from the combat plane is 18 units. Objects at Z = 0 render at 1.0× scale. Objects at Z = -10 render at 0.78× scale. Objects at Z = +10 render at 1.35× scale.

## 1.2 Rendering Pipeline Specifications

### GPU Requirements:
- **Minimum:** GPU supporting WebGL 2.0 / OpenGL ES 3.0 / Vulkan 1.0
- **Recommended:** GPU supporting WebGPU / Vulkan 1.2 / DirectX 12
- **Target:** 60 FPS at 1920×1080 with all effects enabled (Quality: High)

### Rendering Technique:
- **Shading model:** Forward+ rendering with deferred light accumulation for dynamic lights
- **Maximum simultaneous dynamic lights:** 32 (point lights), 8 (spot lights), 2 (directional)
- **Shadow maps:** Cascaded shadow maps for directional light (3 cascades: 512×512, 1024×1024, 2048×2048). Point light shadows: cubemap at 512×512 per light, maximum 8 simultaneous shadow-casting point lights.
- **Anti-aliasing:** TAA (Temporal Anti-Aliasing) at High quality, FXAA at Medium, none at Low
- **HDR rendering:** 16-bit floating point render target (RGBA16F) for proper bloom and exposure
- **Tone mapping:** ACES filmic tone mapping curve
- **Color space:** sRGB output, linear internal rendering

### Character Rendering:
- **Mesh type:** Skinned mesh with GPU vertex skinning (maximum 4 bone influences per vertex)
- **Material model:** Simplified PBR — metallic/roughness workflow with albedo, metallic, roughness, normal, and emissive maps
- **Shader complexity budget:** Maximum 150 GPU instructions per character pixel (fragment shader)
- **Draw calls per character:** 3-5 (body, armor overlays, weapon, glow effects, trail)
- **Maximum simultaneous characters on screen:** 60 (1 player + up to 59 enemies)
- **Character LOD levels:** 3 — Full (0-15 units from camera), Medium (15-25 units, 50% bone count, simplified materials), Low (25+ units, billboard sprite replacement)

### Post-Processing Chain (executed in this exact order):
1. Ambient Occlusion (SSAO) — 1.2ms GPU budget
2. Bloom — 0.8ms GPU budget
3. Depth of Field — 0.6ms GPU budget
4. Motion Blur — 0.7ms GPU budget
5. Chromatic Aberration — 0.2ms GPU budget
6. Color Grading (LUT) — 0.3ms GPU budget
7. Vignette — 0.1ms GPU budget
8. Film Grain — 0.1ms GPU budget
9. Tone Mapping — 0.2ms GPU budget
10. FXAA/TAA (if applicable) — 0.8ms GPU budget
11. UI rendering — 0.3ms GPU budget

**Total post-processing GPU budget: 5.3ms at 1920×1080**

Total character height: approximately 1.75 units (head-to-toe).

### Step 2: Bone Rotation Axis Convention
- Y-axis = up (primary bone direction)
- X-axis = left (positive = character's left)
- Z-axis = forward (positive = character's forward)
- All joint rotations are Euler XYZ order
- Rotation limits per joint:
  - Spine joints: ±30° X (flexion/extension), ±20° Z (lateral bend), ±15° Y (twist)
  - Shoulder/clavicle: ±30° Y, ±20° Z
  - Upper arm: -180° to +30° X (flexion), ±90° Y (rotation), -90° to +10° Z (abduction)
  - Lower arm: 0° to -150° X (elbow flexion only), ±20° Y (forearm rotation)
  - Hand: ±45° X, ±30° Z
  - Head/neck: ±45° X, ±60° Y, ±30° Z
  - Upper leg: -120° to +30° X (hip flexion/extension), ±30° Y, ±45° Z
  - Lower leg: 0° to +150° X (knee flexion ONLY — no backward bending)
  - Foot: ±30° X, ±20° Z

### Step 3: Retarget Process
For EVERY downloaded mocap clip:
1. Import source animation into Blender
2. Align source skeleton T-pose to stickman T-pose using a mapping file:
   - source_Hips → PELVIS
   - source_Spine → SPINE_01
   - source_Spine1 → SPINE_02
   - source_Spine2 → SPINE_03
   - source_Neck → NECK_01
   - source_Head → HEAD
   - source_LeftShoulder → CLAVICLE_L
   - source_LeftArm → UPPER_ARM_L
   - source_LeftForeArm → LOWER_ARM_L
   - source_LeftHand → HAND_L
   - source_RightShoulder → CLAVICLE_R
   - source_RightArm → UPPER_ARM_R
   - source_RightForeArm → LOWER_ARM_R
   - source_RightHand → HAND_R
   - source_LeftUpLeg → UPPER_LEG_L
   - source_LeftLeg → LOWER_LEG_L
   - source_LeftFoot → FOOT_L
   - source_RightUpLeg → UPPER_LEG_R
   - source_RightLeg → LOWER_LEG_R
   - source_RightFoot → FOOT_R
3. Apply bone-length scaling: source bone rotations are preserved, but translational components are scaled to stickman proportions
4. Clamp all joint rotations to the limits defined in Step 2
5. Export as the engine's native animation format
6. Log any frames where clamping was applied (these need manual review)

### Step 4: Quality Check Per Clip
After retargeting, each clip must pass:
- No joint exceeds rotation limits
- No foot penetrates ground plane (Z=0) during grounded animations
- No self-intersection (limbs passing through torso)
- Root position is consistent (no floating or sinking)
- Loop points are seamless (for looping animations)
- Animation plays correctly at 30, 60, 120, and 144 FPS without artifacts

## 3.2 Per-Bone Variation Formula

For each bone B at frame F:

```
final_rotation(B, F) = 
    base_mocap_rotation(B, F)                           // The retargeted mocap data
    + context_offset(B, context_variables)              // From variable influence map
    + perlin_noise(unique_seed, F, bone_frequency(B))   // Organic variation, ±1-5° per joint
    + combo_escalation_modifier(B, combo_count)         // Escalating exaggeration
    + sword_character_modifier(B, equipped_sword)       // Sword-specific body language
    + transition_blend(B, previous_animation, current)  // Smooth connection to prior anim
```

### Perlin Noise Specifications:
- **Frequency per bone:** 2-4 Hz (smooth, organic — never jittery)
- **Amplitude per bone:** ±1° to ±5° (spine gets ±1°, hands get ±5° — distal joints have more variation)
- **Each bone uses a different noise seed offset** so no two joints move identically
- **Noise is 3D** (affects X, Y, Z rotation independently with different phase offsets)

# 4. CONTEXTUAL ANIMATION LIBRARY — EXACT SPECIFICATIONS

## 4.1 Running — 5 Variants (Full Frame Data)

### Variant 1: STANDARD RUN
- **Trigger:** velocity 40-70% max, health > 50%, stamina > 30%, no enemies within 5m, straight-line movement for > 0.5s
- **Cycle duration:** 0.45 seconds per full stride cycle at 100% speed
- **Stride length:** 1.2 units per cycle
- **Body angle:** 8° forward lean from vertical
- **Pelvis rotation:** ±12° around Y-axis (alternating)
- **Pelvis vertical oscillation:** ±0.04 units (sine wave, peaks at flight phase)
- **Knee flexion at contact:** 160° (nearly extended)
- **Knee flexion at loading:** 120° (deep compression)
- **Ankle dorsiflexion at toe-off:** 40°
- **Arm swing:** ±35° from neutral, elbows fixed at 90°
- **Head stabilization:** counter-rotates ±3° to maintain forward gaze
- **Foot ground contact time:** 35% of cycle
- **Flight phase:** 15% of cycle
- **Transition to other states:** 6-frame crossfade to walk, 4-frame burst to sprint, 3-frame into jump

### Variant 2: COMBAT APPROACH RUN
- **Trigger:** enemies within 10m, any velocity building, combat state active
- **Cycle duration:** 0.40 seconds per stride (10% faster than standard)
- **Body angle:** 15° forward lean
- **Sword arm:** held at 45° upward behind body, blade pointing back, elbow at 110°
- **Free arm:** extended forward at shoulder height, fingers spread for balance
- **Knee flexion:** 10° deeper than standard run at every phase (lower center of gravity)
- **Stride length:** 0.9 units (shorter, more controlled)
- **Head:** turns toward nearest enemy every 0.8 seconds (takes 4 frames to turn, 8 frames tracking, 4 frames return)
- **Lateral movement:** slight weaving pattern — 0.15 units side-to-side per stride cycle
- **Foot contact:** forefoot-first (no heel contact)

### Variant 3: DESPERATE SPRINT
- **Trigger:** health < 30% OR stamina < 20% OR fleeing boss attack AND velocity > 80% max
- **Cycle duration:** 0.30 seconds per stride (fastest possible)
- **Body angle:** 25° forward lean (nearly horizontal)
- **Stride length:** 1.8 units (maximum possible)
- **Knee drive:** knees reach 90° flexion during flight phase (high knee action)
- **Arm swing:** full range, ±60°, elbows open wider than normal
- **Head:** ducked low, every 1.2 seconds quick backward glance (3 frames)
- **Foot contact:** forefoot ONLY, ground contact time: 20% of cycle
- **Breathing overlay:** chest heaves ±6° rotation, every 0.4 seconds
- **Instability:** ±3° random body sway per stride (simulates exhaustion)
- **Stumble recovery:** 5% chance per stride cycle of a micro-stumble (0.2s correction animation)

### Variant 4: TACTICAL RETREAT RUN
- **Trigger:** velocity is backward relative to nearest enemy angle, any health
- **Cycle duration:** 0.50 seconds (slower — moving backward is harder)
- **Body angle:** facing enemy, 0° lean (upright), knees bent 30°
- **Stride:** short quick steps, 0.5 units per cycle
- **Sword arm:** blade extended toward enemy at chest height
- **Free arm:** extended sideways at 45°, palm facing forward
- **Foot contact:** toe-first, checking ground (slight downward glance every 1.5 seconds, 5 frames)
- **Weight shift:** continuous side-to-side, ±0.1 units, period 0.8 seconds
- **Head:** locked on nearest enemy (does not turn away)

### Variant 5: ADRENALINE DASH-RUN
- **Trigger:** combo_count > 20 AND style_rank >= A AND velocity > 90% max
- **Cycle duration:** 0.25 seconds (near-superhuman speed)
- **Body angle:** 35° forward lean
- **Stride length:** 2.2 units
- **Foot contact:** barely touching, ground contact time: 10% of cycle
- **Flight phase:** 50% of cycle (nearly gliding)
- **Arm position:** trailing behind body, relaxed, fingers streaming
- **Head:** lifted, looking at next target with what reads as confidence
- **Energy aura:** constant particle emission from body outline
- **Afterimage:** permanent 3-frame afterimage trail even without dashing
- **Ground effect:** energy streak on ground beneath feet, matching sword element color
- **Skip-step:** every 3rd stride, one leg does a small hop-skip instead of full stride (visual flair)

## 4.2 Jumping — 5 Variants (Full Frame Data)

### Variant 1: STANDARD COMBAT JUMP
- **Trigger:** jump button from grounded, no strong directional input, velocity < 50% max
- **Total air time:** 0.70 seconds
- **Peak height:** 2.5 units
- **Takeoff (frames 0-8, 0.13s):**
  - Frames 0-3: knees compress to 90°, center of mass drops 0.15 units (anticipation)
  - Frames 4-6: explosive extension, knees go from 90° to 170° in 3 frames
  - Frames 7-8: toes push off, ankles reach 50° plantar flexion
- **Ascent (frames 9-18, 0.15s):**
  - Legs tuck to 120° knee flexion
  - Arms rise to shoulder height

## 4.4 Death Animations — Enemy (Full Phase Specifications)

### Phase 1: Death Trigger (frames 0-2, 33ms at 60fps)
- Frame 0: `is_dying` flag set, current animation interrupted
- Frame 0-1: body freezes in current pose (hit-stop, 2 frames)
- Frame 2: death animation begins
- Variant selection based on `killing_blow_type`:
  - Light attack → quick stagger (body jolts 10° in attack direction)
  - Heavy attack → violent jolt (body jolts 25° + lifts 0.1 units)
  - Charged attack → launch (body lifts 0.5 units, all limbs extend)
  - Aerial attack → spike down (body driven toward ground at 45°)
  - Dash attack → freeze-then-launch (1 frame freeze, then velocity in dash direction)
  - Elemental → element-specific death state begins (see sword specs)
  - Finisher → extended sequence (3-8 seconds, unique per sword + combo seed)

### Phase 2: Body Response (frames 2-10, 133ms)
- Force application per body fragment:
  - `directional_force` = attack_direction × attack_force_magnitude × (1.0 + random(-0.1, 0.1) from seed)
  - `upward_force` = attack_weight × 3.0 units/s (light=1.0, medium=2.0, heavy=3.0, charged=5.0)
  - `angular_velocity` = hit_location_offset_from_center × directional_force × 0.5 rad/s
  - `random_rotation_offset` = perlin_noise(unique_seed, fragment_id) × 15° (per fragment)

### Phase 3: Fragment Physics (frames 10-180+, 2.5+ seconds)
- Each fragment is an independent rigid body:
  - Mass: head=0.5kg, torso=3.0kg, upper_arm=0.8kg each, lower_arm=0.5kg each, upper_leg=1.2kg each, lower_leg=0.8kg each
  - Gravity: -9.81 units/s²
  - Ground collision: bounce coefficient 0.3, friction 0.7
  - Rotation damping: 0.95 per frame
  - Lifetime: 3.0 seconds before dissolution begins
- Energy burst at separation points:
  - Particle count: 10 (light kill) to 50 (charged kill) per separation
  - Initial velocity: 2-8 units/s outward from separation point
  - Lifetime: 0.5-1.5 seconds per particle
  - Color: exact hex per sword (see Section 7)

### Phase 4: Dissolution (frames 180-300, 2.0 seconds)
- Dissolve begins at frame 180 from death
- Each fragment dissolves independently with staggered timing (random offset 0-30 frames from seed)
- Dissolve pattern: edge-burning inward over 60 frames
- Dissolve color: sword element primary color, emissive at 2.0× intensity
- Rising particles: 5-15 small embers per fragment, float upward at 1 unit/s, fade over 1.0s
- After all fragments dissolved: no trace remains

# 7. ENEMY DESIGN — COMPLETE AI SPECIFICATION

## 7.1 Enemy AI Decision Tree (per type)

### GRUNT — Decision Tree:
```
EVERY 0.5 seconds, evaluate:
├── IF distance_to_player > 8 units: MOVE TOWARD player at 3 units/s
├── IF distance_to_player 3-8 units: 
│   ├── IF ally_count_nearby > 3: CIRCLE at 2 units/s (flanking behavior)
│   ├── IF ally_count_nearby 1-3: APPROACH at 4 units/s
│   └── IF ally_count_nearby = 0: HESITATE (slow to 2 units/s, occasional stop)
├── IF distance_to_player < 3 units:
│   ├── IF player_is_attacking AND facing_toward_me: 
│   │   ├── 60% chance: BLOCK (2.0s duration)
│   │   └── 40% chance: DODGE backward (dash 3 units back)
│   ├── IF player_is_recovering: ATTACK (random from 4 attack options)
│   └── IF player_is_idle: ATTACK (aggressive, shortest wind-up)
└── IF health < 20%:
    ├── 30% chance: FLEE (run away from player for 3s)
    └── 70% chance: ENRAGE (attack speed +20%, defense -30%, for 5s)
```

### STALKER — Decision Tree:
```
EVERY 0.3 seconds (faster evaluation = more reactive):
├── IF player_is_attacking: FLANK (move perpendicular to player at 6 units/s)
├── IF behind_player: ATTACK IMMEDIATELY (fast multi-hit, 0.2s wind-up)
├── IF in_front_of_player AND distance < 4: DODGE sideways (0.15s reaction)
├── IF distance > 5: APPROACH using indirect path (curved, 5 units/s)
├── IF distance < 2: RAPID COMBO (3-5 hit sequence, then disengage)
└── AFTER attacking: RETREAT 3 units, wait 0.5-1.5s (random), re-engage
```

### PHALANX — Decision Tree:
```
EVERY 1.0 seconds (slow evaluation = deliberate):
├── ALWAYS: face player, advance at 2 units/s
├── IF player_attacks_from_front: RAISE SHIELD (blocks all frontal damage)
├── IF player_is_behind: TURN (0.8s turn animation, vulnerable during turn)
├── IF player_attacks_from_side: SHIELD BASH (if player is within 2 units)
├── IF player_is_distant: CHARGE (3 units/s for 1.5s, shield forward)
└── IF health < 30%: GROUND POUND (AoE attack, 5 unit radius)
```

### ELITE — Decision Tree:
```
EVERY 0.2 seconds (fastest evaluation — reacts like a player):
├── IF player_attacks:
│   ├── 30%: PARRY (6-frame perfect window, if successful → guaranteed counter)
│   ├── 40%: DODGE (directional, away from attack arc)
│   └── 30%: BLOCK (reduced damage taken)
├── IF player_is_recovering: COMBO ATTACK (3-7 hit sequence with mixed light/heavy)
├── IF distance > 5: DASH ATTACK (close distance + attack in one motion)
├── IF distance < 3: MIXUP (randomly choose: grab throw, rapid combo, or backward dash to reset)
├── IF own_health < 25%: DESPERATION MODE (attack speed +30%, stop blocking, all-in offense)
└── PATTERN AVOIDANCE: tracks player's last 5 responses, avoids repeating patterns that were punished
```

## 9.1 Input Buffer Specifications:
| Input | Buffer Window | Priority | Notes |
|-------|--------------|----------|-------|
| Light Attack | 200ms (12 frames at 60fps) | Normal | Queued during current attack, executes on first valid frame |

| Sword Ability | 300ms (18 frames) | Low | Longest buffer — abilities have long wind-ups |
| Directional Input | 0ms (instant) | Highest | Always read from current frame, never buffered |

## 9.2 Attack Cancel Window Specifications:
Each attack has defined "cancel windows" where the player can interrupt the recovery animation:

```
Attack Structure:
[WIND-UP] → [ACTIVE] → [FOLLOW-THROUGH] → [RECOVERY]
   ↑           ↑              ↑                  ↑
 no cancel   no cancel    early cancel       late cancel
                           window             window

Early cancel window: frames FOLLOW-THROUGH to FOLLOW-THROUGH+4 (4 frames)
  → Can cancel into: dash, jump, different attack type
Late cancel window: frames RECOVERY to RECOVERY+6 (6 frames)  
  → Can cancel into: any action

Example: Light Attack 1
  Wind-up: frames 0-4 (5 frames, no cancel)
  Active: frames 5-8 (4 frames, hitbox active, no cancel)
  Follow-through: frames 9-14 (6 frames, early cancel at frame 9-12)
  Recovery: frames 15-26 (12 frames, late cancel at frame 15-20)
  Total: 27 frames (0.45 seconds at 60fps)
```

## 9.3 Perfect Timing Windows:
| Action | Window Size | Success Effect | Failure Effect |
|--------|-----------|----------------|----------------|
| Parry | 6 frames (100ms) | Full counter-attack, enemy stunned 1.5s | Normal block (reduced damage) |
| Perfect Dash | 5 frames (83ms) | Pass through attack unharmed, 0.3s slow-mo, next attack empowered | Normal dash (might get hit) |
| Just Frame (heavy attack) | 3 frames (50ms) at apex of charge | 150% damage, unique animation variant | Normal charged attack |

# 12. NON-NEGOTIABLE QUALITY STANDARDS

## These are absolute requirements. No exceptions. No compromises.

1. **No animation shall ever repeat identically.** The PAVE system guarantees uniqueness through 30+ context variables, per-combo seeds, and per-joint perlin noise. If two frames are visually identical across different combos, the system has failed.

2. **No foot shall ever penetrate the ground.** The ground plane at Y=0 is absolute. Physics and animation are synchronized. If a foot goes below Y=0 without an intentional ground-slam attack, the system has failed.

3. **No input shall ever be ignored beyond its buffer window.** If the player presses a button and nothing happens within the specified buffer window, the system has failed.

4. **No animation transition shall contain a visible snap.** A snap is defined as any joint rotating more than 30° in a single frame during a transition. If snapping is visible, the transition system has failed.

5. **No sword trail shall deviate from the blade's actual trajectory by more than 5% of blade length.** If the trail appears disconnected from the sword, the trail system has failed.

6. **No frame shall exceed the performance budget.** 16.67ms at 60 FPS. If any frame exceeds this, optimizations have failed. The 1% low FPS must not drop below 50 FPS.

7. **No enemy shall use the same animation set as another enemy type.** Each type has unique movement personality, attack patterns, reactions, and deaths. If two types look similar, the differentiation has failed.

8. **No combo shall be visually identical to a previous combo with the same inputs.** The dynamic combo generation system plus PAVE guarantee uniqueness. If two combos look the same, the seed system has failed.

9. **No death shall be visually identical to a previous death.** The death assembly system uses 10+ variables to guarantee uniqueness. If two deaths look the same, the system has failed.

10. **No effect shall exist without a visible gameplay cause.** Every visual effect must be traceable to a specific action. If the player cannot understand why an effect appeared, the effect communication has failed.

11. **No mocap clip shall be used without retargeting validation.** Every clip must pass the quality check in Section 2.3 Step 4. If any clip fails and is used anyway, the pipeline has failed.

12. **No feature shall be added while fundamental locomotion remains broken.** If the running cycle looks wrong, no new combat features are to be developed until it is fixed. Period.

13. **No claim of improvement shall be made without test verification.** Every fix must be verified by at least one automated test AND visual inspection in the debug views. Untested fixes are not fixes.

14. **No post-processing effect shall be applied without budget verification.** The total post-processing budget is 5.3ms. If any combination of effects exceeds this, the quality settings system has failed.

15. **No assumption shall be made — only measurements.** If the specification says "hit-stop is 5 frames," it is 5 frames. Not 4, not 6. Exact values are specified throughout this document for a reason. Follow them.

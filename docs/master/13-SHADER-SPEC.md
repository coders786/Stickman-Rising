# 13 — SHADER & BAKE SPECIFICATION (Phase 6b, implementation-ready)
**Serves:** D3 (GPU technology) · D7 (single canvas, bake-time only) · `06` §3.

This is the document M2/M3 implement. It contains actual shader math, actual
sample counts, actual precision qualifiers, and the bake budget. Nothing here
runs per frame — in the default path **no shader executes during play at all**
(D7), so the constraint is a **one-off bake budget**, not fill rate.

> **Consequence worth stating loudly:** `06` §3's per-frame fill arithmetic
> (10 M noise lookups/frame) does **not** apply to the shipping path. It applies
> only to the desktop B1 experiment. At bake time we can afford 10–20 samples per
> pixel because we pay it once, and the budget that replaces it is
> "≤6 ms per plate, ≤3 plates per run start" (§7).

---

## 1. Three decisions that shape every shader below

### 1.1 Texture fetches beat computed noise — on mobile especially
Evidence: "GPU's are highly optimized for texture lookups. Any reasonable noise
function is going to be slower than a texture lookup… a single octave of a
gradient noise function using a highly optimized hashing function is about **35 %
slower** than a texture lookup" (id Software–era practitioner, r/gamedev);
peer-reviewed work replacing texture-based Perlin with FNV1/Jenkins/Murmur
hashes reports only "very close performance compared to a texture based Perlin
noise implementation", i.e. hash-based noise's win is *freeing bandwidth*, not
speed (`https://arxiv.org/abs/1903.12270`); mobile GPU descriptions confirm
texture samplers fetch/filter 4–8 texels per cycle in fixed-function hardware
that is "far more power- and area-efficient than general ALUs", with the return
path as the thing you hide latency behind
(`https://medium.com/@ankitsingh.mailbox/mobile-gpu-hardware-pipeline-df310aca0956`).

Counter-evidence, also true: procedural noise "doesn't suffer from texture
compression, texture size, or bit fidelity issues" (same thread) and can be
evaluated at 32-bit while an RGBA8 atlas gives 8-bit. We accept 8-bit for the
octaves that feed *cloud density*, because the final image is 8-bit anyway and
the octaves are weighted (0.5/0.25/0.125/0.0625) so quantisation lands below the
output LSB after the sum.

**Decision S-1: octaves come from a generated noise atlas (4 octaves in RGBA),
not from per-pixel hash chains.** The atlas is itself generated by a shader at
boot, so the pipeline stays asset-free (REQ-706) and seed-varied.

### 1.2 mediump is the default, and it is load-bearing
Research: `mediump` is 16-bit; "floats are actually 16 bits, not 32 bits (when
using mediump precision, which you almost always will be in WebGL)" and bit-hack
hashing *requires* highp (`https://snowing.dev/articles/shader_noise.html`);
mobile sampler hardware can quantise UVs to 16 bits, producing "blocky,
pixelated artifacts when the UV range grows too large… values are cleanly
quantized" (`https://discussions.unity.com/t/force-low-precision-float-on-unity-editor/742983`);
`mediump` is up to 2× faster and 2× more power-efficient on Adreno and MDN says
don't require highp in fragment shaders (`06` §3 sources).

**Decision S-2: every fragment shader is `precision mediump float;` with a
documented highp escape hatch (§4). UVs are wrapped before they are scaled.**

### 1.3 Plates are written, not blended
`readPixels` returns raw framebuffer values **bottom-up**, and `putImageData`
expects **straight (unpremultiplied) alpha, top-down**.

**Decision S-3: plate shaders output straight alpha with blending disabled, into
a per-plate FBO whose vertex shader flips Y.** No un-premultiply pass, no
JS-side row flip, no `UNPACK_FLIP_Y_WEBGL` confusion (that flag does not apply to
`readPixels`). Getting this wrong produces upside-down or haloed clouds and is
the most likely week-one bug in M2.

## 2. The noise atlas

```
size      512 × 512 RGBA8, mipmapped (levels 0..9), REPEAT, LINEAR_MIPMAP_LINEAR
channel   R = octave 1 (period 4)   G = octave 2 (period 8)
          B = octave 3 (period 16)  A = octave 4 (period 32)
content   tileable value noise, period-locked (integer periods ⇒ seamless wrap)
seed      profile.seed → int, mixed with the existing avalanche mixer
cost      512² = 262 k px × 4 octaves ≈ 1.05 M hash evals [E]
mem       1.00 MB + mips ≈ 1.33 MB [E]
gen time  ≤ 5 ms [T] on any WebGL2 device (one quad, 262 k fragments)
```

Why 5 bits of period per channel and not more: FID-11..13 need coverage bands,
not detail. Detail beyond the 4th octave is supplied by the *plate resolution*
(1024×576) and by the shaping curve, not by more octaves.

Sampling rule: **one `texture()` returns four octaves at once**, so a 4-octave
fBm is **1 fetch** if all octaves share the same UV, or 4 fetches if each octave
is scaled separately (they are, because lacunarity 2 means octave *n* samples at
`uv * 2^n`, which cannot reuse one channel). The atlas therefore saves on ALU,
not on fetch count:

| Method | ops per fBm(4) |
|---|---|
| hash-chain fBm (classic) | 4 × (floor, fract, 4 hashes, 3 mixes) ≈ **18–24 ALU + 16 hash ALU** |
| atlas fBm (4 fetches, one channel each) | 4 × `texture()` + 3 mixes ≈ **4 fetch + 6 ALU** |
| atlas fBm (single fetch, 4 channels summed) | **1 fetch + 3 ALU** — used for low-frequency mass only |

**Tier rule:** `low`/`medium` use the single-fetch 4-channel sum for the base
mass and 2 extra warped fetches; `high`/`ultra` use per-octave fetches.

## 3. Program inventory (bake-time only)

All programs render a full-screen quad into an FBO sized to the ladder step.
`plateGen` is the only program that is "procedural noise"; the rest consume its
output.

| Program | Purpose | Fetches/px | ALU est. | Output | Tier variants |
|---|---|---|---|---|---|
| `P_atlas` | generate the noise atlas (4 octaves + blue-noise dither in a 64×64 corner) | 0 | ~60 (highp hash) | 512×512 RGBA8 | once per seed |
| `P_sky` | 4-stop vertical gradient + horizon glow + star field + haze band | 1 | ~20 | 1024×576 RGBA8 | stars: 400/900/2000/3200 |
| `P_moon` | disc + corona rings + angular rays + deck glitter mask | 2 | ~34 | 256×256 (or 384×384 ultra) | rings 2/3/3/4 |
| `P_cumulus` | domain-warped fBm → shaped density mask, lit top / shadow base | **10–12** | ~48 | 1024×576 RGBA8 | warp 1/2/2/2, octaves 3/4/4/4 |
| `P_stratus` | anisotropic fBm bands, low contrast, seamless | 5 | ~22 | 1024×576 RGBA8 | bands 1/2/3/3 |
| `P_cirrus` | 4:1 stretched fBm, alpha-only wisp | 3 | ~14 | 1024×576 RGBA8 | stretch 3/4/4/5 |
| `P_grade` | apply 3D LUT to a plate (bake-time colour grade) | 2 (src + LUT) | ~10 | same size | — |
| `P_dither` | merge 1-LSB triangular dither into alpha | 1 | ~6 | same size | on for `low`/`medium` |

Total distinct programs: **8**, of which 6 are used on a phone. All are compiled
and linked once at boot, behind a hidden 1×1 probe canvas, and **no program is
compiled during a run** (REQ, FID-31 "0 ms first-frame hitch").

## 4. Precision map (the part that silently ruins mobile shaders)

| Value | Precision | Why |
|---|---|---|
| `v_uv` (0..1) | mediump | fine — small magnitude, interpolated |
| `uv * scale` (scale up to 32) | **mediump, wrapped first** | 16-bit float has ~10 bits of mantissa; 32× is still <2^5, so fine **if** you `fract()` before multiplying again |
| world-space coordinate | **highp** | can exceed 1024; 16-bit UVs would quantise visibly (Unity thread) |
| `gl_FragCoord.xy` | **highp** | screen-space; precision loss shows as 1-px stair-steps |
| hash integers (atlas gen only) | **highp int** | bit-shift hashing needs 32-bit (snowing.dev) |
| LUT lookup coordinate | mediump, clamped | 16³ over 4096×16 strip; error < 1 texel |
| colour accumulators | mediump | 8-bit output; extra bits are wasted |
| dither | mediump | ±1/255 |

Rule: **a shader that needs highp in a fragment stage must say so in a comment
and explain the magnitude that forces it.** `highp` in a fragment shader is the
portability trap MDN warns about and the performance trap Adreno rewards you for
avoiding.

## 5. Shader math (abbreviated, but exact where it matters)

### 5.1 Cumulus — the only complex one
```
// all in mediump; uv wrapped before scaling (S-2)
vec2 warp1 = (texture(uAtlas, uv * 0.9 + uWind * uT).rg - 0.5) * uWarpAmp;   // 1 fetch
vec2 warp2 = (texture(uAtlas, (uv + warp1) * 2.3).rg - 0.5) * uWarpAmp*0.5;  // 1 fetch
vec2 p     = uv + warp1 + warp2;

float n = 0.0;                                                              // 4 fetches
n += sum4(texture(uAtlas, p * 3.0)) * 0.5333;     // R+G+B+A, the "mass" term
n += sum4(texture(uAtlas, p * 7.0)) * 0.2667;     // detail
n += sum4(texture(uAtlas, p * 15.0)) * 0.1333;    // edge break-up
n += sum4(texture(uAtlas, p * 31.0)) * 0.0667;    // micro (ultra only)

float cover = uCoverage;                                   // 0.22..0.38 (FID-11)
float d     = smoothstep(cover - uSoft, cover + uSoft, n);  // silhouette shaping
float lift  = smoothstep(cover, cover + 0.35, n);           // lit top
vec3  col   = mix(uShadowCol, uLitCol, lift);               // from the profile
float a     = d * uOpacity;
```
`sum4` is `dot(texel, vec4(1.0))` — one instruction, four octaves.

Fetches: warp1 (1) + warp2 (1) + 4 sums (4) = **6**, plus 2 for the silhouette
break-up pass on `high`+, plus 2 for the lit-side sample = **10–12**. That is
half the sample count of the classic 18–54 hash-chain version in `06` §3, with
better noise quality (8-bit quantisation is below the visible step after the
0.53/0.27/0.13 weights).

**Lit/shadow direction** comes from a 2D light vector projected into the plate:
`lift` is biased by `dot(normalize(grad(n)), uLightDir)`, giving cloud tops lit
on the correct side and bases in the palette's cool shadow (REQ-404). One
gradient estimate via 2 extra taps is cheaper than 3-tap finite differences and
is only enabled on `high`+.

### 5.2 Stratus
```
float band = sin(uv.y * uBands * PI + texture(uAtlas, uv * vec2(0.6, 3.0)).r * 2.0);
float n    = sum4(texture(uAtlas, uv * vec2(1.7, 5.0)));
float a    = smoothstep(0.35, 0.75, n * 0.75 + band * 0.25) * uOpacity;  // ΔL ≤ 0.18 (FID-12)
```
3–5 fetches, no warping: stratus is *supposed* to be flat, so no domain warp is
needed — a rare case where the cheaper shader is also the more correct one.

### 5.3 Cirrus
```
vec2 q = mat2(1.0, 0.0, 0.0, 0.25) * uv;      // 4:1 stretch (FID-13)
float n = sum4(texture(uAtlas, q * 9.0));
float w = smoothstep(uCoverage, uCoverage + 0.25, n) * (0.35 + 0.65 * n); // wispy tails
```
2–3 fetches. Elongation is enforced by the matrix, not by the noise, so FID-13's
≥4:1 is a *construction invariant* rather than something we tune.

### 5.4 Sky
Four-stop vertical ramp (zenith → mid → horizon → ground haze) from the profile,
plus a horizon-relative haze band and a star field from the atlas's blue-noise
channel thresholded per tier. **No per-pixel `sin`/`cos` for stars** — the atlas
exists; use it.

### 5.5 Moon
Disc + 2–4 corona rings + angular rays from `atan2` quantised to 64 sectors,
modulated by the atlas. Rays fade with `moonCover` from weather (REQ-205), so one
program produces the whole `moonCover` set.

## 6. Grading at bake (the 3D LUT)

```
strip   4096 × 16 RGBA8  =  16³ texels  =  256 KB          (16 KB per LUT, 2 resident)
lookup  manual two-slice blend (no hardware trilinear across slices):
          c0 = texel(strip, f(b), g, r, slice i)
          c1 = texel(strip, f(b), g, r, slice i+1)
          out = mix(c0, c1, fract(b*15))
why     hardware filtering bleeds across slice boundaries in a strip layout
dither  triangular ±1 LSB, from the atlas A channel at a different scale
bands   ΔE 6–18 by target (FID-19); soft target 10
```
Sources: 16³ = 16 KB and the strip layout with manual slice blending
(`https://scanmountgoat.github.io/Smush-Material-Research/post_processing/colorgradinglut/`);
3D LUT = one dependent texture read (`GPU Gems 2`, ch. 24).

Mid-run weather change does **not** re-bake plates: it cross-fades two already
baked plates (REQ-504) and, if a grade shift is needed, a single tint blit.

## 7. Bake budget — one plate per frame, never a 25 ms spike

The existing cold bake is 20.4–25.7 ms **[M]** in one go. We do not repeat that
mistake. Instead:

```
run start (existing fade, ≤2.5 s):
  frame 0   atlas (≤5 ms)  + sky plate (≤6 ms)   → 11 ms, inside the fade
  frame 1   cumulus plate (≤6 ms)
  frame 2   stratus plate (≤6 ms)
  frame 3+  cirrus / moon / grade passes only if the frame still has slack
rule:      at most ONE plate per frame; each plate bake ≤6 ms;
           if a plate would exceed 6 ms, halve the ladder step and bake that instead
```

| Tier | Plate px | Est. bake/plate | Plates | Total |
|---|---|---|---|---|
| low | 512×288 = 147 k | 1.5–2.5 ms | 2 | ≤5 ms |
| medium | 768×432 = 332 k | 3–4 ms | 3 | ≤12 ms |
| high | 1024×576 = 590 k | 5–6 ms | 4 | ≤24 ms |
| ultra | 1280×720 = 922 k | 7–9 ms | 5 | ≤45 ms (spread over 5 frames) |

Estimates `[E]` from the measured 0.6 ms/plate average of the existing Canvas2D
bake **[M]** scaled by pixel count and a 1.4× GPU-vs-CPU advantage **[J]**; the
first real number replaces this table in M2's report.

**Readback + upload per plate** (the part people forget):
```
readPixels  590 k px RGBA  → 2.36 MB Uint8Array           ~1.5–3 ms [E]
ImageData   new ImageData(new Uint8ClampedArray(buf.buffer), w, h)   ~0 ms (zero-copy wrap)
putImageData into the plate canvas                        ~1–2 ms [E]
```
So a "6 ms" plate is really ~2 ms shader + ~4 ms readback/upload. If a phone
cannot do that, the ladder step drops — the plate gets smaller, never later.

## 8. Known failure modes (pre-registered, so we recognise them)

| Symptom | Cause | Guard |
|---|---|---|
| Upside-down clouds | `readPixels` is bottom-up | S-3 Y-flipped vertex shader; assert on a known asymmetric test pattern |
| Halos / dark fringes | premultiplied vs straight alpha mismatch | S-3 straight-alpha output, blending disabled |
| Blocky sky at large UVs | 16-bit UV quantisation | wrap before scaling; highp for world-space |
| Banding in gradients | 8-bit LUT + 8-bit plate | §6 dither, 1 LSB triangular |
| Visible tile seam | non-periodic noise | period-locked atlas, seam probe at bake (M-ELONG sibling) |
| NaN / black corner | `pow(0.0, x)` / `normalize(0)` | clamp before pow; `max(len, 1e-5)` |
| Shimmer on drift | sub-texel motion | integer offsets only (P2) |
| First-frame hitch | program compiled on first draw | compile all 8 at boot behind the probe |
| Different colours per browser | colour space of readback | treat plates as sRGB-encoded bytes end to end; never convert |

## 9. Tier variants (one shader source, `#define` variants)

```
#define OCTAVES 3|4|4|4
#define WARP_LEVELS 1|2|2|2
#define SAMPLE_LIT_SIDE 0|0|1|1
#define STARS 400|900|2000|3200
#define MOON_RINGS 2|3|3|4
```
Variants are compiled from **one** source string with defines injected, so a
shader cannot drift between tiers. Tests assert that every define combination
used by a tier links successfully (headless compile check where possible; on
device otherwise).

## 10. What this spec does *not* cover

* The per-frame desktop B1 experiment (still specified in `05`/`06`; gated by P4).
* WebGPU ports (P5; ultra-only; must match `ΔE ≤ 1`).
* Gameplay drawing (untouched, Rule 10).
* Art direction of the palettes (`03`, `mood.ts` — the colours above are inputs).

## 11. Open questions

1. **Atlas 512 vs 256:** 256² halves memory and generation time but may show
   tiling at the 4th octave on `ultra`. Prototype in M2; the atlas is one number.
2. **8-bit octaves:** if quantisation shows as contour lines in the stratus band,
   store the two lowest octaves in RG16F on `high`+ (adds 0.5 MB, keeps mediump
   sampling).
3. **Atlas per run vs per profile:** per run gives per-run cloud texture
   (stronger S1 distinctness) at ≤5 ms cost; per profile is cheaper but two runs
   of the same archetype share cloud texture. **Proposed: per run** — it is the
   cheapest way to buy visible procedurality, which is what the user asked for.

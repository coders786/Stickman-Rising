    39→# 1. RENDERING PARADIGM — 2.8D DEPTH-AWARE PERSPECTENCE
    40→
    41→## 1.1 Dimensional Definition
    42→
    43→This is NOT a flat 2D game. This is NOT a 3D game. This is **2.8D** — defined as follows:
    44→
    45→- **Gameplay plane:** All gameplay-critical movement, hitbox detection, collision, and combat mechanics operate on a 2D plane (Z = 0). Input is mapped to X (horizontal) and Y (vertical) axes on this plane.
    46→- **Rendering pipeline:** The entire visual output is rendered using a 3D rendering pipeline with perspective projection. Characters, enemies, and key gameplay objects are 3D meshes rendered with perspective correction.
    47→- **Depth layering:** The environment extends into Z-space across 6 distinct parallax layers (specified in Section 10). Each layer moves at a defined rate relative to camera motion.
    48→- **Z-axis excursions:** Characters MAY move along the Z-axis during specific scripted sequences (cinematic dashes, finishers, dodge rolls). These excursions are limited to ±5 units from the combat plane, are camera-controlled, last no more than 1.5 seconds, and do NOT affect gameplay hitboxes (the character's combat hitbox remains locked to Z = 0 during the entire excursion).
    49→- **Perspective correctness:** Objects closer to the camera render larger. The perspective FOV is 35° (vertical). Camera distance from the combat plane is 18 units. Objects at Z = 0 render at 1.0× scale. Objects at Z = -10 render at 0.78× scale. Objects at Z = +10 render at 1.35× scale.
    50→
    51→## 1.2 Rendering Pipeline Specifications
    52→
    53→### GPU Requirements:
    54→- **Minimum:** GPU supporting WebGL 2.0 / OpenGL ES 3.0 / Vulkan 1.0
    55→- **Recommended:** GPU supporting WebGPU / Vulkan 1.2 / DirectX 12
    56→- **Target:** 60 FPS at 1920×1080 with all effects enabled (Quality: High)
    57→
    58→### Rendering Technique:
    59→- **Shading model:** Forward+ rendering with deferred light accumulation for dynamic lights
    60→- **Maximum simultaneous dynamic lights:** 32 (point lights), 8 (spot lights), 2 (directional)
    61→- **Shadow maps:** Cascaded shadow maps for directional light (3 cascades: 512×512, 1024×1024, 2048×2048). Point light shadows: cubemap at 512×512 per light, maximum 8 simultaneous shadow-casting point lights.
    62→- **Anti-aliasing:** TAA (Temporal Anti-Aliasing) at High quality, FXAA at Medium, none at Low
    63→- **HDR rendering:** 16-bit floating point render target (RGBA16F) for proper bloom and exposure
    64→- **Tone mapping:** ACES filmic tone mapping curve
    65→- **Color space:** sRGB output, linear internal rendering
    66→
    67→### Character Rendering:
    68→- **Mesh type:** Skinned mesh with GPU vertex skinning (maximum 4 bone influences per vertex)
    69→- **Material model:** Simplified PBR — metallic/roughness workflow with albedo, metallic, roughness, normal, and emissive maps
    70→- **Shader complexity budget:** Maximum 150 GPU instructions per character pixel (fragment shader)
    71→- **Draw calls per character:** 3-5 (body, armor overlays, weapon, glow effects, trail)
    72→- **Maximum simultaneous characters on screen:** 60 (1 player + up to 59 enemies)
    73→- **Character LOD levels:** 3 — Full (0-15 units from camera), Medium (15-25 units, 50% bone count, simplified materials), Low (25+ units, billboard sprite replacement)

  1160→# 12. NON-NEGOTIABLE QUALITY STANDARDS
  1161→
  1162→## These are absolute requirements. No exceptions. No compromises.
  1163→
  1164→1. **No animation shall ever repeat identically.** The PAVE system guarantees uniqueness through 30+ context variables, per-combo seeds, and per-joint perlin noise. If two frames are visually identical across different combos, the system has failed.
  1165→
  1166→2. **No foot shall ever penetrate the ground.** The ground plane at Y=0 is absolute. Physics and animation are synchronized. If a foot goes below Y=0 without an intentional ground-slam attack, the system has failed.
  1167→
  1168→3. **No input shall ever be ignored beyond its buffer window.** If the player presses a button and nothing happens within the specified buffer window, the system has failed.
  1169→
  1170→4. **No animation transition shall contain a visible snap.** A snap is defined as any joint rotating more than 30° in a single frame during a transition. If snapping is visible, the transition system has failed.
  1171→
  1172→5. **No sword trail shall deviate from the blade's actual trajectory by more than 5% of blade length.** If the trail appears disconnected from the sword, the trail system has failed.
  1173→
  1174→6. **No frame shall exceed the performance budget.** 16.67ms at 60 FPS. If any frame exceeds this, optimizations have failed. The 1% low FPS must not drop below 50 FPS.
  1175→
  1176→7. **No enemy shall use the same animation set as another enemy type.** Each type has unique movement personality, attack patterns, reactions, and deaths. If two types look similar, the differentiation has failed.
  1177→
  1178→8. **No combo shall be visually identical to a previous combo with the same inputs.** The dynamic combo generation system plus PAVE guarantee uniqueness. If two combos look the same, the seed system has failed.
  1179→
  1180→9. **No death shall be visually identical to a previous death.** The death assembly system uses 10+ variables to guarantee uniqueness. If two deaths look the same, the system has failed.
  1181→
  1182→10. **No effect shall exist without a visible gameplay cause.** Every visual effect must be traceable to a specific action. If the player cannot understand why an effect appeared, the effect communication has failed.
  1183→
  1184→11. **No mocap clip shall be used without retargeting validation.** Every clip must pass the quality check in Section 2.3 Step 4. If any clip fails and is used anyway, the pipeline has failed.
  1185→
  1186→12. **No feature shall be added while fundamental locomotion remains broken.** If the running cycle looks wrong, no new combat features are to be developed until it is fixed. Period.
  1187→
  1188→13. **No claim of improvement shall be made without test verification.** Every fix must be verified by at least one automated test AND visual inspection in the debug views. Untested fixes are not fixes.
  1189→
  1190→14. **No post-processing effect shall be applied without budget verification.** The total post-processing budget is 5.3ms. If any combination of effects exceeds this, the quality settings system has failed.
  1191→
  1192→15. **No assumption shall be made — only measurements.** If the specification says "hit-stop is 5 frames," it is 5 frames. Not 4, not 6. Exact values are specified throughout this document for a reason. Follow them.
